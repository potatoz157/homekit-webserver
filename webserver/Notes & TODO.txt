File Input Analysis:
    - RAG --> vector database along with chunked raw text
        - better for massive numbers of unstructured database, unlimited indexing scale (much larger size capacity)
        - cheaper upfront, slower and expensive per query
        - better at locating text
        - LLM is fed raw text chunks (located by comparing text embeddings by similarity score and fetching the corresponding text for the vector embedding)
    - LLM WIKI --> synthezised, linked markdown files (generated upon upload prior to user query)
        - better for deep, interconnected knowledge (like research, notes, etc.)
        - higher upfront cost to build, instant and cheaper to query, limited indexing scale (cannot search as much content)
        - better at understanding structure/architecture and logic flow 
        - LLM is fed contents of markdown files directly

    Storing File Steps: (assumes RAG)
    1. Parse files and extract text
    2. Split text into chunks (i.e. into 500 token chunks -- maybe with some overlap in content?)
    3. Feed the chunks into a text-embedding model (use a model specifically for generating text embeddings)
    4. Store vector based embeddings into a vector database along with the raw text chunk

    Query Steps: (user asks question about file(s) -- assumes RAG)
    1. Feed user input into text-embedding model (same model as before)
    2. Compare vector embedding to those in the database using similarity score (e.g. cosine similarity)
    3. Pull out the raw chunk/text of the matching vector embeddings from the database
    4. Feed the question and retrieved text chunk into the LLM with a specific prompt, for example:
        [LLM PROMPT]
        Anser the user's question using ONLY the provided text context below.

        CONTEXT:
        "...." (this is the retrieved raw text chunk)

        USER QUESTION:
        "...." (this is the user prompt)


    Generic Chatbot Experience (including file upload):
    - for a normal chatbot, the user may or may not upload files
    - if no file is uploaded, text-embedding model should not run prior to the LLM (the embedding model should not run at all in this case)
    - if there are files uploaded, but the user asks a question unrelated to the files, the embedding model should not run either
        - How do you classify whether the user is asking about previously uploaded files or not?
        1. Use a manual switch/toggle: 'Search Files ON/OFF'
            - easy to implement, requires manual input
        2. Use a very light LLM to classify for you: e.g. tell the llm to classify the user prompt into FILE_SEARCH or GENERAL_CHAT
            - more compute, but feasible if a fast, lightweight model is found
        3. Always use text embedding model and let the LLM decide whether to use retrieved file context
            - much more compute and expensive, safest/most accurate, but might take much longer (more tokens)
